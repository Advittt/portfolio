Passive to Active, how autonomizing my claude code session led to my account being suspended

April 1st, 2026 Autonomous AI Agents Claude Code
[Update - April 29, 2026] I got my account back! "Upon receiving your appeal, we investigated this decision and reinstated your account. We apologize for any inconvenience." 🎉

I set out to build a personal AI assistant inspired by J.A.R.V.I.S.. Not just a chatbot, but something closer to an operating system layer:

  • voice-driven
  • modular
  • capable of delegating tasks
  • composed of smaller, specialized agents

There are a few different users of claude code, the business users who understand the product and service whom build tools the intended way, then there are the engineers who think more abstract, blinded by optimization, efficiency and curiosity, which can lead us to exploring uncharted edge cases.

My Idea - Passive

Jarvis is a local voice assistant that runs on the user's Mac. Modern day Siri, Alexa, Google Home, constantly listen in to our conversations without us prompting to wake them. Jarvis has key principles:

  • Locality - the voice and speech all runs locally on my computer and does not make any requests unless I explicitly call “Jarvis”.
  • Transparent - Use open source code and libraries to increase visibility of how Jarvis works and allow Jarvis to understand its own architecture. This way it can improve itself too upon request.
  • Customizable - Having an ability to connect to and add as many subagents as I desired for different purposes meant it was scalable and free to interact with whatever I wanted to - home devices like lights, garage, social media, Slack, Calendar, etc.
  • Portable - using Claude Dispatch, I want the ability to connect to Jarvis while I am away form my computer. Complete tasks while I am in the gym, cinema, networking events, etc.
  • Active.

Old Architecture

Where Things Got Interesting

Initially, every interaction followed a clean lifecycle:

spawn → respond → exit

Since I had to use python to inject the speech to text into the CLI, a new claude -p "<message>" subprocess is spawned and exits after producing a response. This is not a persistent process - it's a "spawn, respond, die" cycle. Okay, so let’s just so lets maintain conversation continuity by passing --continue on subsequent calls, restoring the full conversation history (messages, tool results, everything).

I thought this idea of using claude code works great because it handles context compaction automatically when the session gets long. Furthermore, the system prompt (from CLAUDE.md ) is re-assembled by Claude Code on every call, but prompt caching means repeated content is served from cache at minimal cost. This is why the Jarvis personality lives in CLAUDE.md rather than being passed as a --system-prompt flag - it gets cached more aggressively and can't lose it's personality!

Nonetheless, this bottleneck of using --continue means I CAN NOT keep subagents alive since they can not be recalled by the main agents memory.

In that case, I will just make subagents their own claude code session and pass in the UUID, --resume <session-id>, so they recall the conversation history and remain isolated to one another, living in separate working directories.

This led to a key realization:

You don’t need short-lived processes. You can build persistent agent sessions.

Jarvis:

  • Simply, a Claude Code session with a simple documentation - has knowledge about how it works, how to add additional subagents, and an configure itself upon users request.
  • main brain and orchestrator
  • can control life cycle of sub agents as well as assign them tasks and commands

‘Sub’agents:

  • All subagents at this point were not exactly sub agents of Jarvis, they were just other claude code sessions but acted like subagents
  • Each subagent has its own Claude Code session with its own CLAUDE.md docs directory, and tool set. This means a subagent only sees the documentation relevant to its domain — the Spotify bot doesn't know about Gmail, and vice versa.
  • Spotify was my first subagent I made as a POC - if I give a claude CLI simple instructions on how to connect to my Spotify API, and pointed it to some python files to show how to perform tasks (tools), can it act as my medium to control an external software? YES!
  • GMail - Now that we have Spotify, can we do the same for GMail and google accounts - yes and even easier now that we have an example to go off of (Spotify)

The Edge Case That Introduced Fuzziness

Each request was isolated. Context was reconstructed each time. This was safe, predictable and aligned with how most AI tooling is intended to work. But it felt… inefficient.

The Shift From Stateless Calls to Active Agents

At this point, the architecture quietly transformed into something else:

a continuously running, multi-agent system capable of acting without direct user prompts - a system of stateful, cooperating agents.

The old architecture meant I have persistent agents who can maintain its own memory, retain context across interactions and behave more like a long-lived process. Now I need to take Jarvis to its final form, Active.

STOP THE BUS

Here is where my planning gets me suspended.

Given my research and exploration, Jarvis will use a python bus to communicate between the agents. I enter an autonomous OS.

Instead of:

  • Advit: “Jarvis, can you check my emails for anyone trying to scheudle a meeting with me”
  • Jarvis: “You have an email from Dario Amodei requesting lunch at 1 pm this Saturday”
  • Advit: “Jarvis, can you add that to my calendar”
  • Jarvis: “Done”

It becomes:

  • Jarvis: “Hey Advit, you got an email from Dario Amodei requesting lunch at 2 pm on Saturday, I added it to your calendar and confirmed with him. I had to reschedule your lunch date with your girlfriend given the conflicts and priority list. I will let you know how she responds.”

I introduce polling for my agents to actively manage my day. Keeping me productive and not wasting time on the standard tedious tasks. This mimics office managers in real life, you don’t micromanage them, they tell you what to do. An autonomous multi-agent system.

I did it, lets go! planning mode and execute! clear context, and auto-accept! Im getting myself a coffee while it does its magic!!!

oh...

What I Missed

The system was technically working, but I hadn’t fully internalized the policy implications of what I was enabling.

In particular:

  • long-lived sessions blur boundaries of control
  • background-style polling introduces autonomy
  • agent-to-agent coordination increases system independence

These aren’t just technical features, they change the operational model. I wasn’t using the official API - I was orchestrating this through repeated CLI/session calls, effectively treating Claude like a backend.

The Result

My access was revoked, my account suspended and under investigation.

At first, that was frustrating.

But stepping back, I understand why.

The system I was converging toward wasn’t just a “tool wrapper” anymore, it was moving into a category that requires much tighter constraints and safeguards.

What I Learned

1. Architecture Shapes Behavior

Small decisions (like session persistence) can fundamentally change what a system is.

2. Autonomy Is a Spectrum

There’s a big difference between responding to a request and continuously acting on behalf of a user.

3. Orchestration Is the Hard Problem

The challenge isn’t calling models, it's coordinating agents, handling failure, managing state safely.

The Key Insight

The biggest realization for me was:

a continuously running, multi-agent system capable of acting without direct user prompts - a system of stateful, cooperating agents.

None of these individually seemed problematic.

Together, they changed the nature of the system entirely.

The Redesign (What I’d Do Now)

If I were to rebuild this system today, I’d keep the same vision, but enforce stricter boundaries.

Principles

  • User-initiated only - No background loops or polling. Use API where necessary and recognize system intentions
  • Ephemeral execution - No long-lived hidden state
  • Explicit orchestration - Every multi-agent step is traceable and intentional
  • Token Management - understand and manage my token usage more carefully.

Why I’m Sharing This

Not because something “went wrong”, but because something important became visible. If you’re building in this space, you will probably run into the same edge.

Final Thoughts

Curiosity led me here.

  • This was purely a personal experiment
  • No reselling, no abuse, no scraping
  • Just exploring multi-agent architectures
  • It was never my intention to break anything or go against the TOS

Just an attempt to understand what becomes possible when you combine orchestration, memory, and modular agents.
